### 2. Установка, окружение и первый рабочий DAG
</summary>

- **Поддерживаемое окружение**
  - Матрица совместимости Airflow, Python, ОС и metadata database
  - Linux и macOS; WSL2 и контейнеры при работе из Windows
  - Виртуальное окружение и отдельная среда для Airflow
  - Требования к CPU, памяти, диску и сетевому доступу
  - Локальная учебная установка и требования промышленного окружения
- **Установка Python-пакетов**
  - Пакет `apache-airflow` и установка через pip
  - Constraints для выбранных версий Airflow и Python
  - Extras и самостоятельные пакеты `apache-airflow-providers-*`
  - Фиксация зависимостей, `pip check` и проверка совместимости
  - Конфликты зависимостей и установка без случайного обновления core
- **Первичная конфигурация**
  - `AIRFLOW_HOME`, `airflow.cfg` и каталоги DAG, логов и плагинов
  - Секции конфигурации и `AIRFLOW__SECTION__KEY`
  - Метабаза SQLite для обучения и PostgreSQL/MySQL для production
  - Инициализация и обновление схемы через `airflow db migrate`
  - Auth manager и способ создания пользователей выбранного менеджера
- **Запуск компонентов Airflow 3**
  - `airflow standalone` как учебный способ запуска
  - `airflow api-server`, `airflow scheduler` и `airflow dag-processor`
  - `airflow triggerer` для отложенного и событийного выполнения
  - Запуск workers согласно установленному executor/provider
  - Проверка версии, health endpoints и доступности интерфейса
- **Официальный Docker-образ**
  - Теги Airflow/Python и фиксация digest образа
  - Расширение образа собственными пакетами и системными библиотеками
  - UID/GID, права томов и отказ от установки зависимостей при старте
  - Docker Compose для локальной распределённой установки
  - Сети, volumes, healthchecks и сохранение метабазы
- **Первый DAG**
  - Создание файла в доступном DAG processor источнике
  - Импорты `DAG`, `dag` и `task` из `airflow.sdk`
  - Две задачи, зависимость и небольшой проверяемый результат
  - `schedule=None`, ручной запуск и просмотр конкретного DagRun
  - Логи, ошибка, retry и повторная проверка результата
- **Инструменты разработчика**
  - VS Code/PyCharm и интерпретатор установленного окружения
  - Структура проекта: `dags`, пакет логики, `tests` и зависимости
  - Ruff, форматирование, pytest и команды локальной проверки
  - `dag.test()` и `airflow tasks test` с учётом ограничений режима
  - Пример конфигурации без секретов и воспроизводимый quickstart
- **Типичные проблемы установки**
  - Несовместимый Python и отсутствующие binary wheels
  - Пакет provider не установлен или содержит другой набор классов
  - Ошибки драйвера БД, миграций, прав каталогов и портов
  - Разные образы или версии кода у компонентов
  - Ошибки DNS, времени системы и подключения к Execution API

### 3. Архитектура Airflow 3 и распределённая модель выполнения
</summary>

- **Компоненты control plane**
  - API server: UI, публичный API и интерфейсы выполнения
  - Scheduler: готовность задач, ограничения и передача executor
  - DAG processor: загрузка кода, discovery и сериализация графов
  - Metadata database: состояние, история и координация
  - Triggerer: асинхронные ожидания и обработка triggers
- **Компоненты выполнения**
  - Executor как адаптер запуска, а worker как исполняющая среда
  - Task runner, supervisor и отдельный процесс пользовательского кода
  - Local, Celery, Kubernetes и Edge-модели выполнения
  - Внешний job, контейнер и TaskInstance как разные сущности
  - Где находятся код, временные файлы, данные и credentials
- **Task SDK и Execution API**
  - Стабильная поверхность `airflow.sdk` для авторов DAG
  - Отделение task runtime от внутренних моделей scheduler
  - Доступ к Variables, Connections и XCom через runtime API
  - Аутентификация, срок действия токенов и доступность API server
  - Версионирование протокола и совместимость worker/control plane
- **Путь от файла до результата**
  - Доставка DAG bundle и обнаружение Python-файла
  - Импорт, построение графа и запись сериализованного представления
  - Создание DagRun и определение готовых TaskInstance
  - Постановка в очередь, запуск, heartbeat и завершение
  - Публикация XCom, asset events, логов и итогового состояния
- **Границы процессов и машин**
  - Parse time, schedule time и execution time
  - Отсутствие общей Python-памяти между задачами
  - Локальный диск worker и доступность файлов другим задачам
  - Потери соединения и неоднозначный результат удалённой операции
  - Управление ресурсами на уровне Airflow и внешнего вычислителя
- **Метабаза и брокер**
  - Состояние оркестрации и данные прикладного конвейера
  - Metadata database и Celery result backend как разные роли
  - Message broker и доставка задания worker
  - DB connection pools и конкуренция компонентов за соединения
  - Критические зависимости и влияние их недоступности
- **Топологии развёртывания**
  - Один узел и LocalExecutor
  - Распределённые Celery workers
  - KubernetesExecutor с отдельным pod на TaskInstance
  - Удалённые и гибридные workers через поддерживаемые executors
  - Разделение контуров по средам, регионам и границам доверия
- **Модель отказов и гарантий**
  - Сбой scheduler, worker, triggerer, API server и метабазы
  - Повторная доставка, orphaned tasks и восстановление состояния
  - Запись внешнего результата до фиксации task success
  - Отсутствие общей транзакции Airflow и внешней системы
  - High availability компонентов и независимая отказоустойчивость данных

### 4. DAG, задачи, запуски и состояния
</summary>

- **Определение DAG**
  - `@dag`, контекстный менеджер `DAG` и явное связывание объектов
  - `dag_id`, описание, tags, owner, owner links и `doc_md`
  - Создание объекта DAG при импорте и правила discovery
  - Уникальность идентификаторов и коллизии между файлами
  - Python-модуль как фабрика описания процесса
- **Параметры DAG и задач**
  - `schedule`, `start_date`, `end_date` и `catchup`
  - `default_args`, явные параметры и приоритет переопределений
  - `max_active_runs`, `max_active_tasks` и версия семантики лимитов
  - `dagrun_timeout`, task timeout и настройки повторов
  - `is_paused_upon_creation` и управление начальным состоянием
  - `allowed_run_types` и ограничение допустимых оснований запуска
  - Display names, owner links и документирование без изменения стабильных IDs
- **DAG и DagRun**
  - Определение процесса и отдельный экземпляр выполнения
  - Scheduled, manual, backfill и asset-triggered запуски
  - `run_id`, logical date и интервал данных
  - Состояния queued, running, success и failed
  - Исторические запуски и версия определения DAG
- **Task и TaskInstance**
  - Operator как описание задачи и TaskInstance как выполнение
  - `task_id`, `run_id`, `map_index` и идентичность экземпляра
  - Попытки, retry history и повторный запуск после clear
  - Параметры определения и runtime context
  - Изменение состояния без выполнения прикладного кода
- **Жизненный цикл задачи**
  - Состояния scheduled, queued и running
  - `up_for_retry`, `up_for_reschedule` и `deferred`
  - `success`, `failed`, `skipped` и `upstream_failed`
  - `removed`, `restarting` и `awaiting_input` в поддерживаемых версиях
  - Допустимые переходы, внешнее вмешательство и state mismatch
- **Завершение запуска**
  - Leaf tasks и вычисление итогового состояния DagRun
  - Влияние `all_done` cleanup-задачи на видимый успех процесса
  - Failed, skipped и upstream_failed как разные причины результата
  - Завершение mapped tasks и групп задач
  - Явные критерии бизнес-успеха и технического успеха оркестрации
- **Изменение и удаление DAG**
  - Pause, unpause, deactivate и удаление метаданных
  - Pause ограничивает планирование и не заменяет отмену внешнего job
  - Переименование DAG/task и влияние на историю
  - Удалённые задачи в уже созданных запусках
  - Сохранение аудита и безопасный вывод процесса из эксплуатации
- **Работа в UI**
  - Список DAG и фильтрация по владельцам и tags
  - Grid, graph, календарь и детали запуска
  - Просмотр попыток, mapped instances, XCom и rendered templates
  - Clear, mark success/failed и область действия операции
  - Различие текущей структуры и исторической версии графа

### 5. TaskFlow API и базовые операторы
</summary>

- **Модель TaskFlow**
  - Декораторы `@dag` и `@task` из публичного SDK
  - Вызов decorated function создаёт задачу при построении DAG
  - Сигнатуры, аргументы и проверяемые контракты функций
  - Возвращаемое значение как XCom и зависимость через XComArg
  - `@result` для явно объявленного результата DAG в Airflow 3.3+
  - Отделение бизнес-функции от инфраструктурной обёртки
- **Композиция Python-задач**
  - Передача результатов между extract, transform и load
  - `multiple_outputs` и именованные результаты
  - `.override()` для повторного использования определения
  - Совмещение TaskFlow и классических operators через `.output`
  - Явные зависимости при отсутствии передачи значения
- **PythonOperator**
  - `python_callable`, `op_args`, `op_kwargs` и context
  - Различие ссылки на функцию и её преждевременного вызова
  - Возврат результатов и управление `do_xcom_push`
  - Импорты и создание клиентов внутри execution time
  - Выбор между `PythonOperator`, `@task` и внешним runtime
- **BashOperator и shell-задачи**
  - `bash_command`, `env`, рабочий каталог и exit code
  - Шаблоны команд и безопасная передача пользовательских параметров
  - Quoting, pipelines, `set -e` и поведение shell
  - stdout/stderr, XCom output и обработка skip-кодов
  - Декоратор `@task.bash` и зависимости от standard provider
- **EmptyOperator и служебные задачи**
  - Пустые узлы для явных границ и объединения веток
  - Стоимость служебных узлов и читаемость графа
  - `EmptyOperator` как современный вариант прежнего `DummyOperator`
  - Документирование task, ссылки и operator extra links
  - Отсутствие вычислений в задаче и бизнес-смысл её статуса
- **Context и выполнение функции**
  - Runtime context и `get_current_context()`
  - Доступ к task instance, DagRun, Params и интервалу данных
  - Контекст внутри функции и недоступность при построении графа
  - Сериализуемые входы и выходы задачи
  - Исключения, skip, fail и предсказуемое завершение
- **Providers и расположение классов**
  - Standard provider для базовых Python/Bash operators
  - Common SQL, HTTP, SMTP и специализированные providers
  - Импорт по документации установленной версии
  - Переезды классов, удалённые aliases и changelog provider
  - Возможности декораторов, зависящие от установки provider
- **Проектирование единицы работы**
  - Один наблюдаемый результат и понятная граница retry
  - Гранулярность задач и накладные расходы оркестрации
  - Обработка небольших данных в Python и вынос тяжёлой работы
  - Минимальные входные зависимости и явные побочные эффекты
  - Повторное использование Python-пакетов вместо копирования DAG-кода

### 6. Время, логические даты и интервалы данных
</summary>

- **Временные понятия Airflow**
  - Logical date как идентификатор семантического времени запуска
  - Data interval как диапазон обрабатываемых данных
  - Фактические времена создания, постановки, начала и завершения
  - DAG `start_date` и фактический `DagRun.start_date`
  - `execution_date` как историческое имя logical date
- **Границы интервала**
  - Полуоткрытый диапазон `[data_interval_start, data_interval_end)`
  - SQL-фильтры без перекрытия соседних интервалов
  - Интервал данных и время, когда запуск становится допустимым
  - Точность timestamp и преобразование временных типов
  - Тестирование отсутствия пропусков и двойной обработки границ
- **Logical date и тип запуска**
  - Семантика scheduled run согласно выбранному Timetable
  - Ручной запуск и явно заданный диапазон обработки
  - Asset/event-triggered run и отсутствие календарного интервала
  - Возможность `logical_date=None` в Airflow 3
  - `run_id` для идентичности запуска при nullable logical date
- **Временные зоны**
  - Aware и naive datetime, UTC и локальная бизнес-зона
  - Pendulum и timezone-aware `start_date`
  - Хранение времени, вычисление расписания и отображение UI
  - DST: пропущенные и повторяющиеся локальные часы
  - Согласование временных зон Airflow, SQL и исходных данных
- **Источники времени в коде**
  - `now()` и `today()` как источник невоспроизводимой обработки
  - Параметры интервала вместо текущего времени worker
  - Заморозка времени в тестах и инъекция clock
  - Timestamp источника, момент доставки и момент обработки
  - Clock skew между компонентами и срок действия токенов
- **Календарь и event time**
  - Бизнес-день и календарный день в разных часовых поясах
  - Поздние события и изменение уже обработанного периода
  - Completeness, lateness и допустимое окно ожидания
  - Watermark конвейера и watermark потокового движка
  - Повторное открытие периода и политика исправления данных
- **Шаблонные представления дат**
  - `ds`, `ts` и форматы без потери исходной семантики
  - Фильтры Jinja для даты и timezone
  - Предыдущие успешные интервалы и отсутствие успешной истории
  - Имена партиций и согласование UTC с бизнес-календарём
  - Ограничения использования `ds` для событийных запусков
- **Временные граничные случаи**
  - Месяцы разной длины, високосный год и конец квартала
  - Переход расписания на другую периодичность
  - Перенос `start_date` после появления истории
  - Пересечение временных окон разных upstream DAG
  - Проверка расписаний на фиксированной временной шкале

### 7. Планирование, Timetables и бизнес-календари
</summary>

- **Способы задания расписания**
  - Параметр `schedule` и замена прежнего `schedule_interval`
  - `None`, `@once`, `@continuous` и presets `@hourly`, `@daily`, `@weekly`, `@monthly`, `@yearly`
  - CRON-выражение, `timedelta` и объект Timetable
  - Asset-based, event-driven и смешанные расписания
  - Явная конфигурация вместо зависимости от значений по умолчанию
- **CRON и интервальное планирование**
  - Пять полей CRON и проверка последовательности запусков
  - `CronDataIntervalTimetable` и `CronTriggerTimetable`
  - Время срабатывания и диапазон данных как отдельные характеристики
  - Влияние timezone, паузы DAG и исторических запусков
  - Настройка `create_cron_data_intervals` и совместимость при миграции
- **Относительные интервалы**
  - `DeltaDataIntervalTimetable` и `DeltaTriggerTimetable`
  - Интервал от начальной точки и календарное выравнивание

### 38. Эксплуатация, диагностика инцидентов и runbooks
</summary>

- **Подход к диагностике**
  - Симптом, воздействие, временной диапазон и последние изменения
  - DAG/run/task/attempt и внешний correlation ID
  - Текущий bottleneck и первичная причина каскада ошибок
  - Безопасная read-only проверка перед изменением состояния
  - Проверка реального результата после восстановления
- **DAG не появляется или устарел**
  - Source/bundle доступен DAG processor
  - Import errors, discovery, `.airflowignore` и duplicate ID
  - Parsing timeout и зависший top-level import
  - Serialized version, refresh interval и задержка доставки
  - Несовпадение dependencies между CI и processor
- **DAG не запускается**
  - Pause, schedule, start/end dates и timezone
  - `max_active_runs`, catchup и отсутствие завершённого интервала
  - Asset conditions и отсутствующие partition events
  - Scheduler health, backlog и блокировки метабазы
  - Ошибка Timetable и последствия изменения расписания
- **Task не получает выполнение**
  - Upstream states, trigger rule и межзапусковые зависимости
  - Pool slots, task/DAG limits и priority
  - Queue без worker или недоступный executor
  - Kubernetes Pending и исчерпанная quota
  - API/broker/database bottleneck и task queued timeout
- **Задача зависла или неожиданно завершилась**
  - Process heartbeat и состояние внешнего job
  - OOMKilled, SIGTERM, eviction и worker restart
  - Socket hang, отсутствующий read timeout и deadlock
  - Ghost/zombie/orphaned execution и state mismatch
  - Решение cancel/reattach/retry на основе фактических side effects
- **Deferred и HITL задачи не продолжаются**
  - Triggerer health, capacity и event-loop blocking
  - Ошибка trigger import/serialization или доступа к секрету
  - Событие получено, но resume method завершается ошибкой
  - Ожидание человеческого ввода, права и timeout
  - Перезапуск triggerer и повтор события без дублирования работы
- **Нет логов или runtime metadata**
  - Live log URL, hostname, network и signing credentials
  - Remote storage permissions и незавершённый upload
  - Execution API auth, token expiry и clock skew
  - XCom backend, serializer и отсутствующий объект
  - Сохранение diagnostics перед удалением pod/worker
- **Деградация производительности**
  - Parse backlog и рост числа DAG versions
  - Scheduler latency и DB locks/connections
  - Celery backlog/prefetch и медленный external service
  - Массовый mapping/backfill и telemetry cardinality
  - Временное ограничение нагрузки и последующее capacity решение
- **Некорректные данные при зелёном DAG**
  - Неполный интервал, неправильная timezone и поздний вход
  - Дубли из retry или пересекающихся runs
  - Cleanup leaf с `all_done` и скрытая upstream failure
  - Зелёный submit operator при failed внешнем job
  - Quality gate, исправление данных и downstream impact analysis
- **Runbook и postmortem**
  - Владелец, SLO, симптомы и диагностические команды
  - Обратимые действия, stop conditions и escalation
  - Порядок clear/backfill и контроль внешних jobs
  - Timeline, contributing factors и проверяемые corrective actions
  - Game days и повторная проверка восстановительных процедур
